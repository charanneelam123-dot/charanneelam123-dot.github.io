AN EXPERIMENT WITH LLAMA 3.2

A longer prompt didn’t fix the citations.

November 18, 2026

What I tested

I compared two prompts using the Llama 3.2 model installed on my desktop. Each answered the same 40 synthetic questions about document facts, missing evidence, calculations, and citation rules. That made 80 real model calls.

What I learned

Both prompts matched the required short answer in 35 of 40 cases. Once citation rules were included, the baseline passed 17 cases and the longer grounded prompt passed 10. Extra sources and bracket-wrapped IDs caused many failures. More instructions didn’t mean better compliance in this run.

A small local experiment with strict answer and citation checks. These scores describe output compliance, not general model accuracy.

01 / INCIDENT ROOM

Keep the investigation
separate from the action.

An outage report is only useful if an operator can check its evidence. Incident Room gathers telemetry, logs, release context, and runbook passages before it proposes a sandbox fix.

Why one agent

A single tool-using agent keeps the investigation state in one place. Read tools accept scoped parameters; each observation gets an evidence ID. The final report must cite real observations and exact quotes.

The tradeoff

Exact quotes catch fabricated references, but they cannot prove that a diagnosis follows from the evidence. The action allowlist is specific to the sample scenarios. Approvals record a sandbox outcome rather than changing a real service.

What was checked

The November 17, 2026 validation record reports 29 passing unit and HTTP tests and three completed scripted incident regressions. Tests cover concurrent approvals, persistence, invalid evidence, and tool budgets. The scripted results do not measure live-model diagnosis quality.

Validation record Engineering notes
02 / WHAT CHANGED?

Make document matching
visible to the reader.

The difficult part of comparing agreements is deciding which clauses correspond. A renamed or moved section should not quietly disappear from the comparison.

How clauses are paired

The matcher uses exact text, unique headings, and token overlap. The report exposes the matching rule. Optional model explanations must quote the source text, so the reader can check the wording.

Where it stops

A rewritten clause can appear as a removal plus an addition. Splitting one clause into two is not a distinct operation. The price parser skips ambiguous amounts and unsupported currencies rather than guessing.

A reproducible sample

The documented sample produces five changed clauses, one moved, one added, one removed, and one unchanged. It calculates two price deltas. For rent, $1,575 − $1,450 = $125 per month. The November 17 record reports 37 passing tests; model adapters were exercised with mocked responses.

03 / AGENT WORKFLOWS

Save the checkpoint before review.

Decision. LangGraph interrupts and SQLite checkpoints preserve a pending workflow. A compare-and-swap reservation prevents two reviewers from resuming the same decision.

Cost. The free hosted instance has ephemeral storage, so a restart can lose checkpoints. Durable deployment needs persistent storage. Exact quote checks establish text membership, not correct interpretation.

Evidence. The November 17 validation records eight passing tests. The suite exercises all ten registered workflows reaching review, reopening the SQLite checkpointer, stale versions, and duplicate decisions. Default tool choices are deterministic; live tool-selection quality remains unmeasured.

04 / DOCUMENT RETRIEVAL

Start with a lexical baseline.

Decision. Filter by company and year, then search a normalized TF-IDF index. A lexical reranking rule combines similarity and term coverage. The default answer exposes source excerpts.

Cost. TF-IDF can miss paraphrases. This implementation uses neither dense semantic embeddings nor a trained cross-encoder. Quote checks do not establish that an answer follows from the quoted passage.

Evidence. The November 17 validation records eight passing tests and successful functional API checks. These verify application behavior; they do not establish retrieval accuracy on a labeled question set. That evaluation is the next step before replacing the baseline.

Validation record
05 / LLM EVALUATION

Keep incompatible runs apart.

Decision. Keep every answer and failed check, with prompt and dataset hashes. The comparison API rejects runs from different datasets or fixture/live modes. MLflow stores aggregate results and version identifiers.

Cost. Term, negation, and citation checks are transparent proxies. They can miss semantic errors. Authored fixture outputs make the harness repeatable but cannot measure a model improvement.

Evidence. The fixture dataset contains twelve versioned cases and two prompt variants. The November 17 record reports eight passing tests, including provider-error recording and incompatible-dataset rejection. A separate local Llama 3.2 evaluation now records 80 real inference calls across 40 cases; the scorecard above publishes every output and its limits.

06 / FRAUD DETECTION

Report the false positives, too.

Decision. Train XGBoost on rolling transaction features, split events chronologically, and choose the decision threshold using validation data only.

Measured result. The saved run uses 5,000 synthetic transactions (seed 41), split into 3,000 training, 1,000 validation, and 1,000 test rows. At a threshold of 0.40, the test set has 14 true positives, 267 false positives, 12 false negatives, and 707 true negatives.

The tradeoff. Roughly 95% of flagged transactions are false positives in this sample. That is too noisy to justify automatic blocking. The result exposes the need for better features and threshold analysis; synthetic data cannot establish performance on real fraud.
